# EF Core Query Performance and Production Tuning

## Introduction
EF Core query performance depends on the SQL generated by the provider, indexes, data distribution, tracking/materialization, number of round trips, and result size. LINQ readability does not guarantee efficient SQL.

```text
LINQ
 ↓ expression translation
SQL
 ↓ optimizer/indexes
database work
 ↓ materialization/tracking
.NET objects
```

## Purpose
The goal is not “make EF faster” in the abstract. The goal is to return the required data with acceptable latency/resource cost while preserving correctness, security, and maintainability.

## Simple example
Bad:

```csharp
var orders = await db.Orders.ToListAsync(ct);
var paid = orders.Where(o => o.Status == OrderStatus.Paid).ToList();
```

This loads the entire table into memory. Better:

```csharp
var paid = await db.Orders
    .AsNoTracking()
    .Where(o => o.Status == OrderStatus.Paid)
    .Select(o => new OrderSummary(o.Id, o.Total))
    .Take(100)
    .ToListAsync(ct);
```

Filtering, projection, and limiting happen in the database.

## What the common execution methods do

EF Core builds an `IQueryable` first. Nothing is sent to the database until an execution/materialization method is called:

```text
Where / Select / OrderBy / Include
        ↓ build query expression
ToListAsync / FirstAsync / CountAsync
        ↓ execute SQL
Database result
.NET value/entity/materialized result
```

### `ToListAsync()`

Executes the query and returns every matching row as `List<T>`:

```csharp
List<OrderSummary> orders = await db.Orders
    .Where(o => o.Status == OrderStatus.Paid)
    .Select(o => new OrderSummary(o.Id, o.Total))
    .ToListAsync(ct);
```

Use it when you genuinely need all matching rows in memory. It returns an empty list when there are no matches. It does not return `null`. Do not use it before filtering, paging, or projection on a large table.

### `FirstAsync()`

Executes the query and returns the first matching row. It throws `InvalidOperationException` when there are no rows:

```csharp
Order order = await db.Orders
    .Where(o => o.Id == orderId)
    .FirstAsync(ct);
```

Use it when a row is required and any matching row is acceptable. If order matters, use `OrderBy` first. If absence is normal, prefer `FirstOrDefaultAsync()` and handle `null`:

```csharp
Order? order = await db.Orders
    .Where(o => o.Id == orderId)
    .FirstOrDefaultAsync(ct);
```

### `SingleAsync()` and `SingleOrDefaultAsync()`

`SingleAsync()` expects exactly one row. It throws when there are zero rows **or more than one row**. This is useful when a uniqueness rule is part of the business contract:

```csharp
Customer customer = await db.Customers
    .Where(c => c.Email == normalizedEmail)
    .SingleAsync(ct);
```

`SingleOrDefaultAsync()` allows zero rows but still throws if duplicates exist. Do not use `FirstAsync()` when duplicate data should indicate corruption; `FirstAsync()` can hide duplicates.

### `CountAsync()`

Executes a `COUNT` query and returns an integer, without loading matching entities:

```csharp
int pendingCount = await db.Orders
    .Where(o => o.Status == OrderStatus.Pending)
    .CountAsync(ct);
```

Use it for totals, validation, quotas, and pagination metadata. `CountAsync()` can still be expensive on a large unindexed predicate; inspect the plan and consider whether an approximate/precomputed count is acceptable.

### `AnyAsync()`

Checks whether at least one matching row exists and returns `bool`. It is usually better than counting when you only need existence:

```csharp
bool hasOpenOrders = await db.Orders
    .AnyAsync(o => o.CustomerId == customerId && o.Status == OrderStatus.Open, ct);
```

The database can stop after finding the first match. Do not write `CountAsync() > 0` when `AnyAsync()` expresses the real question.

### `ExecuteUpdateAsync()` and `ExecuteDeleteAsync()`

These execute set-based database operations without loading entities or using the change tracker:

```csharp
int cancelled = await db.Orders
    .Where(o => o.Status == OrderStatus.Pending && o.CreatedAt < cutoff)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(o => o.Status, OrderStatus.Cancelled), ct);
```

They are efficient for bulk changes, but domain events, navigation behavior, audit logic, and in-memory tracked entities are not automatically updated. Use them only when the bypassed behavior is understood and handled separately.

### Cancellation and exceptions
All async methods should receive the request/worker `CancellationToken`. Cancellation normally throws `OperationCanceledException`; treat request cancellation/shutdown differently from a database fault. `FirstAsync`/`SingleAsync` failures represent data-contract violations and should be mapped intentionally at the application boundary.

## Professional company-level investigation

```text
Capture endpoint/parameters
Log generated SQL safely
Capture actual database plan
Compare estimated/actual rows
Check query count/materialization
Check indexes/locks/memory
Fix one cause and re-measure
```

Common fixes include projection, removing accidental N+1 queries, adding a measured index, paging, split queries for large graphs, and reducing repeated enumeration.

## Advanced choices
Compiled queries can help extremely hot, stable query shapes after profiling. Raw SQL can be appropriate for provider-specific/tuned queries but must remain parameterized and tested. `Include` is not automatically better than projection; it can create huge joins or cartesian multiplication.

Do not use `ToList()` merely to “make the error go away.” It often moves expensive work from SQL to application memory and hides a translation/design issue.

## Comparison
| Technique | Benefit | Risk |
|---|---|
| Projection | Less data/materialization |
| `AsNoTracking` | Lower read overhead |
| `Include` | Convenient graph load | Huge joins/N+1 assumptions |
| Split query | Avoids cartesian graph joins | More round trips |
| Compiled query | Hot stable shape | Complexity/limited applicability |
| Raw SQL/Dapper | Explicit provider control | Manual security/schema responsibility |

## Expert perspective
EF Core is an abstraction over a physical database, not a replacement for database knowledge. Senior engineers know exactly when a LINQ expression becomes SQL, how many rows/round trips it produces, and what the database plan does with it.
